# Building a Merged ESP32-S3 Firmware with ESP-IDF, GitHub Actions, and Docker

When building an ESP32-S3 application with ESP-IDF, the build process generates separate binaries for the bootloader, partition table, and application. If a single firmware image is needed for flashing, these files can be merged into one `.bin` file.

This guide shows two ways to build a merged ESP32-S3 firmware image:

1. **GitHub Actions**
2. **Docker**

Both methods use **ESP-IDF v4.4** and produce the same merged firmware binary.

---

## 1. ESP-IDF Project

The example project has the following structure:

```text
esp32s3/
└── project/
    ├── CMakeLists.txt
    ├── sdkconfig.defaults
    └── main/
        ├── CMakeLists.txt
        └── main.c
```

### `main/main.c`

```c
#include <stdio.h>
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"
#include "esp_log.h"

static const char *TAG = "HELLO";

void app_main(void)
{
    ESP_LOGI(TAG, "Hello World from ESP32-S3!");

    while (1) {
        ESP_LOGI(TAG, "ESP32-S3 is running...");
        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}
```

### `main/CMakeLists.txt`

```cmake
idf_component_register(
    SRCS "main.c"
    INCLUDE_DIRS "."
)
```

### Root `CMakeLists.txt`

```cmake
cmake_minimum_required(VERSION 3.5)

include($ENV{IDF_PATH}/tools/cmake/project.cmake)

project(esp32s3-hello-world)
```

### `sdkconfig.defaults`

```ini
CONFIG_IDF_TARGET="esp32s3"
```

# 2. Building with GitHub Actions

GitHub Actions can build the project automatically using Espressif's ESP-IDF CI action.

Create:

```text
.github/workflows/build.yml
```

with:

```yaml
name: ESP32-S3 Build

on:
  push:
  pull_request:
  workflow_dispatch:

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout repo
        uses: actions/checkout@v4
        with:
          submodules: 'recursive'

      - name: ESP-IDF build and merge
        uses: espressif/esp-idf-ci-action@v1
        with:
          esp_idf_version: v4.4
          target: esp32s3
          path: '.'
          command: |
            idf.py build
            cd build
            esptool.py --chip esp32s3 merge_bin \
              -o esp32s3-hello-world-merged.bin \
              @flash_args

      - name: Prepare firmware
        run: |
          mkdir -p firmware
          cp build/esp32s3-hello-world-merged.bin firmware/

          echo "Firmware:"
          ls -lh firmware/

      - name: Upload firmware
        uses: actions/upload-artifact@v4
        with:
          name: esp32s3-firmware
          path: firmware/esp32s3-hello-world-merged.bin
```

The workflow performs two important operations:

```bash
idf.py build
```

followed by:

```bash
esptool.py --chip esp32s3 merge_bin \
  -o esp32s3-hello-world-merged.bin \
  @flash_args
```

The `@flash_args` file is generated by ESP-IDF and contains the correct addresses and flash configuration for the project.

The resulting artifact is:

```text
esp32s3-hello-world-merged.bin
```

---

# 3. What Does the Merged Binary Contain?

A normal ESP-IDF build produces separate images:

```text
build/
├── bootloader/
│   └── bootloader.bin
├── partition_table/
│   └── partition-table.bin
└── esp32s3-hello-world.bin
```

These are normally written to different flash addresses:

```text
0x00000  bootloader
0x08000  partition table
0x10000  application
```

`esptool.py merge_bin` combines these into a single image:

```text
esp32s3-hello-world-merged.bin
```

This means the complete firmware can be written starting at:

```text
0x00000
```

instead of handling multiple files and offsets separately.

# 4. Building with Docker

Docker provides another way to build the same project without installing ESP-IDF and its toolchain directly on the host.

First pull the ESP-IDF image:

```bash
docker pull espressif/idf:v4.4
```

Assume the project is located at:

```text
~/esp32s3/project
```

Enter the project directory:

```bash
cd ~/esp32s3/project
```

---

## 5. Build the ESP-IDF Project

Run:

```bash
docker run --rm \
  -v "$PWD:/project" \
  -w /project \
  espressif/idf:v4.4 \
  idf.py build
```

The project is mounted into the container:

```text
Host                         Container

~/esp32s3/project  ───────→  /project
```

The generated `build/` directory therefore remains on the host.

---

# 6. Build and Merge in One Command

The complete process can be performed in a single Docker command:

```bash
docker run --rm \
  -v "$PWD:/project" \
  -w /project \
  espressif/idf:v4.4 \
  bash -c '
    idf.py build &&
    cd build &&
    esptool.py --chip esp32s3 merge_bin \
      -o esp32s3-hello-world-merged.bin \
      @flash_args
  '
```

After the command completes:

```text
project/
└── build/
    └── esp32s3-hello-world-merged.bin
```

You can check it with:

```bash
ls -lh build/esp32s3-hello-world-merged.bin
```

---

# 7. GitHub Actions vs Docker

Both approaches use the same underlying ESP-IDF build process.

|                          | GitHub Actions          | Docker          |
| ------------------------ | ----------------------- | --------------- |
| Build location           | GitHub runner           | Local machine   |
| ESP-IDF installation     | Containerized by action | Docker image    |
| Automated builds         | Yes                     | No              |
| Local development        | Less convenient         | Very convenient |
| Reproducible environment | Yes                     | Yes             |
| Output                   | Merged `.bin`           | Merged `.bin`   |

### GitHub Actions

Useful for automated builds:

```text
Git push
   ↓
GitHub Actions
   ↓
ESP-IDF v4.4
   ↓
idf.py build
   ↓
merge_bin
   ↓
firmware artifact
```

### Docker

Useful for local builds:

```text
Source code
   ↓
Docker
   ↓
ESP-IDF v4.4
   ↓
idf.py build
   ↓
merge_bin
   ↓
merged firmware
```

# 8. Final Firmware

The main output of both methods is:

```text
esp32s3-hello-world-merged.bin
```

Unlike the application-only `.bin`, this merged image contains the complete flash image:

```text
┌──────────────────────────────┐
│ Bootloader                   │
├──────────────────────────────┤
│ Partition Table              │
├──────────────────────────────┤
│ ESP32-S3 Application         │
└──────────────────────────────┘
```

Therefore, a single `.bin` can be used instead of separately handling the bootloader, partition table, and application binaries.

The important command that creates it is:

```bash
esptool.py --chip esp32s3 merge_bin \
  -o esp32s3-hello-world-merged.bin \
  @flash_args
```

Using `@flash_args` lets ESP-IDF provide the correct flash addresses and configuration automatically.
